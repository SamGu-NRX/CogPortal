# Recognition integration evidence for Opus

The immediate gap is platform support: the pinned Recognition plugin has no `discovery()` or `submission_from_discovery()`. All five pinned projects contain recognition and enrollment operations. Their ability to bind and score remains untested; static presence is not a passing result.

Source: CogPortal `49f6a98f75eee39fcf38c800d879ca1382558e04`; Week 2 benchmark export `source/week2/` at `c177cf23cdd4f8dbe55401a2eb4bada4c64d37c2`. Student files were read with `git show` at the full pins in `cases.json`, never from modified cache working files. Paths below are relative to each repository or the benchmark package. No student code was executed for this handoff.

## Existing platform contract

- `facial_recognition_benchmark/plugins.py:23–116` declares Recognition v2, runs lifecycle scenarios and scores known identification, unknown rejection and post-enrollment recognition. In contrast, Clustering supplies its real-photo fixture, role and acceptance predicate at `plugins.py:256–302`, then wraps the discovered chain at `304–309`.
- `drivers.py:99–181` requires a fresh application per scenario, enrollment of named known identities, queries, enrollment of the previously unknown identity, and further queries using the same application. Public shuffled batches mix labels; query order is not an identity signal. `adapters.py:27–87` accepts a factory receiving the benchmark-owned FaceNet model and an `enroll`/`recognize` object, with one existing Reynaldo compatibility surface.
- `drivers.py:236–261` requires exactly one string or `None` per image. It does not normalize `"Unknown"`. `metrics.py:50` counts only `None` as rejection. Reading a student's existing unknown sentinel is therefore necessary protocol translation; inventing a classifier is not.
- Existing machinery already describes per-item stages, side inputs, mutation and constructor/method chains (`python/cogbench/src/cogbench/pipeline.py:120–207`, `259`, `3044`). `discovery_spec.py:34–124` already provides end-to-end acceptance, store arrangements, resources, empty-store factories and answer readers. Recognition needs a benchmark-owned description and replay of its lifecycle using that machinery. This evidence does not establish that every required binding form already works.

## Missing operations and acceptance evidence to require

1. Bind and replay enrollment and query against the **same fresh student store** throughout a scenario, then reset between scenarios. Asterisk's globals and absolute module-relative pickle writes need explicit evidence of isolation; a temporary current directory alone is insufficient.
2. Preserve the benchmark model resource and student face-selection, distance and rejection behavior. Translate arrays/paths, tuple fields, prediction dictionaries and unknown sentinels without supplying matching arithmetic. Zero/multiple face output needs an explicit benchmark policy rather than silently dropping images or choosing a new face rule.
3. Exercise two known identities with multiple enrollment images, shuffled held-out known and unknown queries, then enroll that unknown identity and repeat mixed queries. Require correct labels, rejection before enrollment, recognition afterward, retention of earlier identities and exact output counts. These are future acceptance cases, not results of this inspection.
4. Repeat the lifecycle with renamed identities and a fresh store. Verify no probe state, cached student database or previous scenario supplies labels. Prove runtime replay uses current photos and state, not discovery fixture objects. Retain separate failures for import/dependency faults, binding refusal, malformed output and poor recognition.

No inspected operation requires a missing student-trained projection or replacement model. These projects use the course FaceNet descriptor model and populate identity databases through enrollment. Existing corpus evidence records prepared Vision images and an unchanged FaceNet checkpoint (`execution/data-identities.json`); that preparation was not repeated here. Dependency/import availability remains separate from data availability and algorithm presence. The earlier five unsupported Recognition rows cannot support conclusions about recognition accuracy.
